# 06 — Logical Processing Order

## الفكرة

فيه فرق بين ترتيب كتابة أجزاء الاستعلام، وترتيب فهم النتيجة منطقيًا، وخطة التنفيذ الفعلية. الترتيب المنطقي يساعدنا نفهم ليه بعض الأعمدة والأسماء متاحة في مكان ومش متاحة في مكان تاني.

## ترتيب مبسّط للاستعلامات الشائعة

| المرحلة | وظيفتها |
| --- | --- |
| FROM / JOIN | تجهيز مصادر البيانات وربطها |
| WHERE | فلترة الصفوف |
| GROUP BY | تكوين مجموعات وحساب التجميعات |
| HAVING | فلترة المجموعات |
| SELECT | حساب أعمدة النتيجة والأسماء البديلة |
| DISTINCT | إزالة الصفوف المتكررة من النتيجة المختارة |
| ORDER BY | ترتيب النتيجة |
| OFFSET / LIMIT | تجاوز عدد من الصفوف ثم تحديد العدد المعاد |

ده نموذج تعليمي مش قائمة بكل تفاصيل SQL؛ فيه أجزاء إضافية زي WITH وwindow functions وعمليات جمع نتائج الاستعلامات. هنشرح GROUP BY وHAVING بالتفصيل لما نوصل لهم.

## الكود

```sql
SELECT first_name, salary * 1.15 AS salary_after_bonus
FROM employees
WHERE salary >= 5000
ORDER BY salary_after_bonus DESC, id;
```

## النتيجة

| first_name | salary_after_bonus |
| --- | --- |
| Maryam | 13800.00 |
| Mai | 11500.00 |
| Amr | 11500.00 |
| Amr | 8050.00 |
| Rana | 5750.00 |
| Kamel | 5750.00 |

نفهمها كالتالي: نبدأ من الموظفين، نختار المرتبات 5000 أو أكثر، نحسب الزيادة، ثم نرتّب من الأكبر للأصغر. `DESC` معناها تنازلي. أضفنا id كترتيب فاصل لو القيم اتساوت.

## ليه Alias مش شغالة في WHERE؟

ده مثال مقصود يطلع خطأ، لأن العمود `salary_after_bonus` مش عمود أصلي ومش متاح كـSELECT alias في WHERE:

```sql
-- مثال غير صحيح
SELECT salary * 1.15 AS salary_after_bonus
FROM employees
WHERE salary_after_bonus > 6000;
```

نكرر التعبير في WHERE:

```sql
SELECT first_name, salary * 1.15 AS salary_after_bonus
FROM employees
WHERE salary * 1.15 > 6000
ORDER BY id;
```

النتيجة حسب id: Amr (3) بقيمة 8050، Mai (4) بقيمة 11500، Amr (6) بقيمة 11500، Maryam (8) بقيمة 13800.

في PostgreSQL الـoutput alias متاحة في ORDER BY، وكمان في GROUP BY في الحالات المدعومة؛ لكنها مش متاحة في WHERE أوHAVING. الترتيب المنطقي وسيلة للفهم، وفيه قواعد خاصة للأسماء لازم نراعيها.

## من SQL لخطة التنفيذ

| الجزء | دوره بشكل مبسّط |
| --- | --- |
| Parser + semantic analysis | تحليل صياغة الاستعلام ثم التحقق من أسماء الجداول والأعمدة والأنواع وبناء تمثيل داخلي |
| Rewrite system | إعادة كتابة الاستعلام عند الحاجة، مثل توسيع الـviews |
| Planner / Optimizer | اختيار خطة مقدّرة التكلفة من خطط بديلة |
| Executor | تشغيل الخطة وإرجاع النتائج |

في الكراسة النموذج Parser → Optimizer → Executor مناسب كبداية، وأضفنا مرحلة rewrite للدقة في PostgreSQL. الـraw parser بيحلل syntax؛ التحقق من وجود جدول أو عمود جزء من التحليل الدلالي، مش مجرد قراءة الكلمات.

الـoptimizer مش ملزم ينفذ المراحل بنفس الترتيب التعليمي؛ ممكن يقدّم فلترة أو يختار طريقة مختلفة للوصول للبيانات، مع الحفاظ على معنى الاستعلام. كمان مش مضمون ينفذ شروط AND أوOR من الشمال لليمين.

## أخطاء شائعة

- الترتيب المنطقي مش تسجيل حرفي للخطوات اللي المعالج بينفذها.
- `LIMIT` من غير ترتيب محدد مش ضمان لنفس الصفوف كل مرة.
- ما تكتبش شرط معتمد على alias من SELECT داخل WHERE لنفس مستوى الاستعلام.
- الـoptimizer بيختار خطة حسب تقديرات، مش ضمان إن اختياره أسرع خطة فعلية في كل حالة.
